# AI WAR — 電脳戦況モニター 設計書

- 作成日: 2026-10-08
- ステータス: 設計確定（実装計画の作成待ち）
- 参考モック: `mockups/`（a-galaxy / b-hex / c-swarm、ダミーデータ）

## 1. 目的

日々生まれ・更新されるAI（LLM、画像・動画・音楽・音声生成、エージェント）の**現在の立ち位置を、客観データにもとづいて可視化する**一般公開Webサイトを作る。

- AIの各陣営を「電脳世界で戦う軍」として描き、見る人は操作せず戦況を**観戦**する。
- ベンチマークの棒グラフではなく、**勢力図・戦闘として見て面白い**ことを最優先する。
- 2022年11月（ChatGPT公開＝開戦）から現在までの推移をタイムラインで再生できる。「去年はGeminiが強かったのに今は…」が一目で分かる。

## 2. 確定した要件

| 項目 | 決定 |
|---|---|
| 見た目 | 組み合わせ案。全体図＝案A「電脳銀河」、惑星内の戦闘＝案C「粒子大戦」、企業のハイライト＝案B |
| 公開形態 | 一般公開Webサイト（GitHub Pages、無料） |
| 収益化 | **しない（非商用）**。非商用ライセンス（CC BY-NC）のデータも利用する |
| 言語 | 日本語と英語の切り替え |
| 戦線 | 7つ：総合・コード・エージェント・画像・動画・音声・音楽 |
| タイムライン | 2022年11月〜現在、月単位 |
| データ更新 | 半自動。毎週自動で取得・計算し、変更提案（PR）を人が承認する |
| スマホ | 縦画面用にレイアウトを組み替える |
| Artificial Analysis | **使わない**（利用規約上、書面許可が必要なため）。品質データがない部隊は「推定」として扱う |
| 演出 | 画面全体の白フラッシュはしない。点滅は1秒に3回まで（§9.5） |
| 再生速度 | 標準（1倍速）＝1か月あたり約1.4秒。速報のある月は自動で減速する（§9.4） |

## 4. システム構成

```
EVAL/
├─ pipeline/                 データ収集と計算（Node.js + TypeScript）
│   ├─ sources/              データ源ごとの取得モジュール（1データ源＝1ファイル）
│   ├─ raw/                  取得した生データ。日付付きで全保存（再計算の元）
│   ├─ curated/              人が確認する情報（YAML）
│   │   ├─ units.yaml        部隊・軍の定義、モデル名→部隊の対応表、規模シグナルの設定
│   │   ├─ announcements.yaml 公式発表の利用者数（出典URL必須）
│   │   └─ events.yaml       戦況速報の文面の上書き・追加
│   ├─ compute/              強さ・規模・確度・イベントの計算 → world.json
│   └─ test/                 計算のテスト（保存済みの生データ見本を使う）
├─ site/                     表示側（Vite + TypeScript + PixiJS）
│   ├─ src/
│   │   ├─ data/             world.json の読み込みと時間補間
│   │   ├─ render/           描画（PixiJS）。銀河・惑星・粒子・霧・演出
│   │   ├─ ui/               HUD・ランキング・詳細パネル・タイムライン（HTML/CSS）
│   │   └─ i18n/             日英の文言
│   ├─ assets/art/           差し替え用の画像（docs/art-requests.md 参照）
│   └─ public/data/world.json
└─ .github/workflows/
    ├─ weekly-update.yml     毎週月曜：取得→計算→検証→PR作成
    └─ deploy.yml            main への反映時に GitHub Pages へ公開
```

### 4.1 設計上の原則
1. **画面は外部サイトに一切アクセスしない**。読むのは `world.json` だけ。表示が速く、データ源の障害がサイトに波及しない。
2. **生データは日付付きで全保存**する。計算方法の変更時に全期間を再計算できる（Epoch ECIの再推定やArenaのモデル削除にも対応できる）。
3. **データ源ごとに失敗を切り離す**。取得失敗や形式変更があれば、そのデータ源は前回値を使い、PRに警告を出す。更新全体は止めない。
4. **画面とデータの境界は `world.json` のスキーマ**とし、形式チェックで守る。

### 4.2 毎週の更新フロー
1. GitHub Actions（毎週月曜）が `pipeline/sources/*` を実行し、`raw/YYYY-MM-DD/` に保存する。
2. `compute` で `world.json` を再生成し、スキーマを検証する。
3. 画面の自動確認を行う（§10.2）。
4. PR「今週の戦況更新」を自動作成する。本文には次を載せる。
   - 強さ・規模の主な変動
   - 新部隊・新モデルの候補（対応表への追加案）
   - 戦況速報の候補（日英）
   - 警告（取得失敗、形式変更、外れ値）
   - PC・スマホのスクリーンショット
5. 人が確認してマージすると、`deploy.yml` が公開する。

### 4.3 world.json（画面とデータの契約）
```jsonc
{
  "generatedAt": "2026-10-12T00:00:00Z",
  "months": ["2022-11", "2022-12", "…", "2026-10"],
  "partialMonth": "2026-10",            // 当月は速報値
  "orgs":   { "google": { "name": { "ja": "Google", "en": "Google" }, "color": "#4c8dff" } },
  "fronts": [ { "id": "general", "name": { "ja": "総合戦線", "en": "General Front" } } ],
  "units":  { "general": { "gemini": { "org": "google", "name": "Gemini" } } },
  "series": {                            // 月ごと。未参戦は null
    "general": { "gemini": [ null, { "s": 82.1, "c": 28.4, "q": "high" } ] }
  },
  "breakdown": {                         // 内訳パネル用。月→データ源ごとの寄与
    "general": { "gemini": { "2026-10": [ { "source": "arena-text", "value": 91.2, "weight": 0.5 } ] } }
  },
  "events": [ { "month": "2025-03", "front": "general", "unit": "gemini",
                "type": "lead_change", "text": { "ja": "…", "en": "…" } } ],
  "sources": [ { "id": "arena-text", "name": "Arena (Text)", "url": "…",
                 "license": "CC BY 4.0", "credit": "…", "asOf": "2026-10-07" } ]
}
```
容量が大きくなった場合は、`breakdown` を戦線ごとの別ファイルに分けて遅延読み込みする。

## 6. 計算方法

### 6.1 強さ s（0〜100）
**考え方**：データ源の生の点数は年々インフレし、採点方法も変わる。そこで**毎月、データ源ごとに「その月の首位との差」に変換**してから合算する。これで全期間を同じ物差しで比べられる。

1. **部隊の生の値 x(k,u,m)**（データ源 k、部隊 u、月 m）
   - ベンチマーク型：その月末までに発売された、その部隊のモデルのうち最高値。前月の値を引き継ぐ。
   - Arena型（対戦レーティング）：その月末に最も近いスナップショットの、部隊内の最高レーティング。3か月以内にスナップショットがなければ欠測とする。
2. **首位との差を「対首位の期待勝率 p」に変換**し、score = 200·p（首位＝100）とする。
   - Arena型：Δ = R(部隊) − R(首位)、p = 1 / (1 + 10^(−Δ/400))
   - 正答率型（%）：Δ = logit(x) − logit(x首位)、p = σ(Δ)
   - 時間型（METR）：Δ = log2(h) − log2(h首位)、p = σ(κ·Δ)
   - 指数型（ECI）：Δ = E − E首位、p = σ(Δ/τ)
   - κ と τ は設定値とし、方法ページに公開する。初期値は段階1で過去データに当てはめて決める。
3. **版の切れ目は別データ源として扱う**。Arena の 2025-05-16 前後、Terminal-Bench 2.0 と 4.0、LiveBench の各リリースなどは、生の値をつなげない。
4. **合算**：その月にデータがあるデータ源だけで重みを正規化し、加重平均する。データ源に載っていない部隊は減点せず、確度だけ下げる。
5. **戦線ごとの重み**（初期値。設定ファイルで変更でき、変更は更新履歴に残す）
   - 総合：Arena text 0.5、ECI 0.5
   - コード：SWE-bench 0.3、Terminal-Bench 0.25、Arena WebDev 0.25、LiveBench 0.2（Aider は 2023-11〜2025-10 の補完）
   - エージェント：METR 0.4、OSWorld 0.25、τ²-bench 0.2、Vending-Bench 0.15
   - 画像・動画・音声・音楽：Arena系 0.6、Design Arena 0.4（ない戦線は存在するデータ源で正規化）
6. **再構成（過去の補完）**：データ源の開始前の月は、現在も表に残っている古いモデルのレーティングと発売日から逆算する。確度は「再構成」とする。
7. **品質データがない部隊**（Suno、Udio、Midjourneyなど）は、同じ戦線内の規模・注目度の順位と、公式発表から推定する。確度は「推定」とし、推定値であることを画面に明記する。
8. 強さは平滑化しない。新型投入による急変をそのまま見せる。

### 6.2 規模 c（戦線内シェア %）
1. シグナルごとに、戦線内の部隊間シェアを計算する。
2. 重み（LLM系戦線の初期値）
   - 利用者数（公式発表）0.45：発表と発表の間は対数で補間し、6か月を過ぎた値は古いものとして確度を下げる。
   - 一般向けの浸透度 0.25：CrUX順位をアクセス量の目安に換算（アクセス ∝ 順位^−1）し、2025-04以降は StatCounter と混ぜる。
   - 企業・開発者の利用 0.20：Ramp 0.12、OpenRouter 0.08。
   - 注目度 0.10：Wikipedia閲覧数。
3. 製品単体の戦線（画像・動画・音声・音楽）は、製品サイトのアクセス順位、公式発表、注目度、アプリ評価数を使う。どのシグナルを使うかは `units.yaml` で部隊ごとに指定する。
4. シグナルが欠けた部隊は、他のシグナルとの比率から補完し、確度を下げる。
5. 3か月の移動平均で平滑化し、戦線内の合計が100%になるよう正規化する。

### 6.3 確度 q と戦場の霧

| q | 条件 | 霧 |
|---|---|---|
| high（高） | 強さのデータ源が2つ以上、かつ規模も実測 | なし |
| medium（中） | 実測のデータ源が1つ | 薄い |
| reconstructed（再構成） | §6.1-6 の逆算 | やや濃い |
| estimated（推定） | §6.1-7 の推定、または開戦初期のデータ空白期 | 濃い |

部隊の確度は、強さと規模の確度のうち低い方とする。

### 6.4 戦況速報（イベント）の自動検出

| 種類 | 条件 | 文面の例（ja） |
|---|---|---|
| new_unit | 部隊が初めて値を持った月 | 「Kling 参戦 — 動画戦線」 |
| new_model | 新モデルが部隊の最高値を更新し、Δs ≥ 3 | 「Gemini 2.5 Pro 投入 — 総合戦線」 |
| lead_change | 強さ首位の部隊が交代 | 「総合戦線で首位交代：GPT → Gemini」 |
| scale_lead_change | 規模首位の部隊が交代 | 「動画戦線で最大勢力が交代：Sora → Veo」 |
| surge | 1か月で \|Δs\| ≥ 5、または Δc ≥ 5pt | 「Claude 急伸 — コード戦線」 |

- 文面は日英のテンプレートで自動生成する。`curated/events.yaml` で上書き・追加・非表示にできる。
- 新モデル名は、データ源のモデル名と発売日から取る。

## 7. 画面（PC・横画面）

### 7.1 銀河の全体図（トップ）
- 中央に総合戦線の巨大惑星を置き、6つの戦線惑星をその周りに配置する。惑星どうしは光るデータストリームでつなぐ。
- 惑星の表面は部隊の領土に分割する。面積＝規模、輝き・前線の押し込み＝強さ。前線の火花は強さが拮抗するほど多くする。
- 企業色の艦隊がストリーム上を移動する。数は「展開戦線数 × 規模」に比例する。
- 右パネル
  - 選択中の戦線のランキング：強さバー、規模バー、前月比の▲▼。順位変動時は行が滑らかに並び替わる。並び順は**強さ順が既定**で、「規模順」に切り替えられる（スマホも同じ）。強さと規模を混ぜた独自の総合点は作らない。
  - 陣営展開表：軍 × 戦線のマトリクス。
- 軍の名前にカーソルを乗せると、全惑星にあるその軍の領土だけを強調表示する（案Bの機能）。
- 確度の低い領土に霧をかける。

### 7.2 惑星へのズーム
- 惑星をクリックすると、カメラがズームインする（イージング付き）。Escまたは「銀河に戻る」で戻る。
- 惑星の内部では、部隊を粒子の群れとして描く（案C）。群れの大きさ＝規模、速さ・輝き・攻勢＝強さ。前線では粒子が衝突して火花が散る。
- 部隊をクリックすると、詳細パネルを開く。
  - 強さ・規模の推移グラフ（2022-11〜現在）
  - 確度
  - **この数値の内訳**：データ源ごとの値、重み、出典リンク

### 7.3 共通のHUD
- タイトル「AI WAR／電脳戦況モニター」と現在の年月（大きな数字）
- 凡例：「領土の広さ＝規模」「輝き・攻勢＝強さ」「霧＝推定を含む」
- 言語切り替え（日本語／EN）、シェアボタン、「データと方法」へのリンク
- 最終更新日。当月は「速報値」と表示する。

## 9. タイムラインと演出

### 9.1 タイムライン
- 範囲は2022-11〜現在。年の目盛りと、速報がある月に印を付ける。
- 操作：再生・一時停止、速度（1倍・2倍・4倍）、ドラッグで任意の月へ移動。キーボード操作（Space、←→）にも対応する。
- 月と月の間は補間して、滑らかに変化させる。

### 9.2 初回の「開戦」演出
- 初めて訪れた人には「2022年11月、ChatGPT参戦」から歴史を標準速度で再生する。現在まで約70秒（速報での減速を除く）。
- スキップと倍速のボタンを常に表示する。2回目以降は現在の月から始める（localStorageで判定し、使えない場合は毎回現在から始める）。

### 9.3 戦況速報バナー
- 速報の月を通過すると、企業色のバナーを表示し、該当部隊の領土を脈動させる。
- 同じ月の速報は順番に表示し、重ねない。

### 9.4 再生速度
- **標準（1倍速）＝1か月あたり約1.4秒**。モックの0.7秒では速すぎて追えなかったため、半分の速さにした。
- 2倍速・4倍速を選べる。
- **速報のある月では自動で減速し、バナーを読み終える時間（約2秒）止まってから進む**。4倍速のときは減速を短くする。
- ドラッグでの移動中は速報を出さない。

### 9.5 光の演出の安全ルール（必須）
- **画面全体の白フラッシュは使わない**。速報時の光は、その軍の色の光を局所的に広げる程度にとどめる。
- 光る演出は輝度変化に上限を設け、**どの領域も1秒間に3回を超えて点滅させない**（WCAG 2.3.1 準拠）。
- 描画層に「フラッシュ予算」を実装し、すべての光る演出はそれを通す。予算を超える要求は弱めるか間引く。
- OSの「視差効果を減らす」設定（`prefers-reduced-motion`）では、粒子の速度・画面の揺れ・光の演出を大きく減らす。

## 10. 動作確認

### 10.1 データ側
- 計算関数（正規化、合算、確度、イベント検出）は、`pipeline/test/` の固定データでテストする。
- 保存済みの生データから `world.json` を作り、期待値と比較するゴールデンテストを置く。
- `world.json` のスキーマ検証を行う。失敗したらPRに「要確認」と表示する。
- データ源ごとに、記録済みのレスポンスで取得処理をテストする。

### 10.2 画面側（PRごとに自動）
- ヘッドレスChromeで開き、開戦から現在まで再生して、コンソールエラーがないことを確認する。
- PC（1440×900）とスマホ（390×844）のスクリーンショットを撮り、PRに添付する。
- フレームレートの目標は、PCで60fps、スマホのエミュレーションで30fps以上。
- フラッシュ予算のテスト：連続して速報を発生させても、1秒3回の上限を超えないことを確認する。

## 12. リスクと対策

| リスク | 対策 |
|---|---|
| データ源の仕様変更・閉鎖 | 生データの全保存、1戦線を複数のデータ源で支える、データ源ごとの失敗の切り離し |
| 順位への批判 | 内訳パネルと方法ページで計算を全公開し、重みの変更は更新履歴に残す |
| データ源の偏り（Arenaは大手有利、OpenRouterは安価モデル寄り） | 複数のデータ源を混ぜ、偏りを方法ページに明記する |
| 公式発表の誤り | 出典URL必須とし、PRで承認する |
| 利用規約・ライセンスの変更 | 非商用・クレジット表記を徹底し、変更時はそのデータ源を外して再計算する |
| 商標 | 企業ロゴを使わず、名前と色で表現する。「各社とは無関係の非公式プロジェクト」と明記する |
| 光過敏性 | §9.5 のフラッシュ予算と `prefers-reduced-motion` 対応 |
| 低性能端末 | フレームレートを監視し、自動で画質を落とす（ブルーム→解像度→粒子数の順） |
